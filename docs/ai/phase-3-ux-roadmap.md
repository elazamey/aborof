# المرحلة الثالثة: تجربة المستخدم والتيسير عبر سيليا

هذه الوثيقة خريطة تنفيذ تدريجية لتسهيلات الواجهة والمساعد الذكي، بنفس المبدأ الصلب:
**نُمطي، مُعلَّم بالميزات، صفر كسر.** كل بند يحدد العلم الذي يحكمه، ومعيار القبول، وطريقة التراجع (إعداد لا كود).

| زر **«تابع طلبك»** يفتح واتساب برسالة مُعدّة | `ChatWidget.tsx` | لا علم | يفتح محادثة واتساب بنص «عايز أتابع حالة طلبي رقم: » |

### كيف وصلت البطاقات بلا كسر
1. أداة `search_products` صارت تُعيد `structuredContent` (نفس مبدأ MCP: `content` + `structuredContent`) مع **حقول الكتالوج فقط** وبحد أقصى 5 عناصر.
2. `runToolLoop` يجمع المحتوى المنظّم من الأدوات الناجحة فقط.
3. `extractProductCards` ينقّيه بعقد zod صارم (`.strict()`): أي حقل غير معروف أو قيمة غير صالحة تُسقط البطاقة، والسقف **3 بطاقات** بلا تكرار.
4. المحرك يضيف `products` إلى النتيجة، و`/api/chat` يُضيفها للحقل نفسه **فقط إن وُجدت**؛ وإلا فشكل الاستجابة القديم `{ reply, source }` كما هو حرفيًا.
5. البطاقات تظهر فقط عند `ENABLE_MCP_TOOLS=true`؛ وعند إغلاقه لا يتغير أي شيء في الواجهة ولا في العقد.

### تحسين إضافي (من مراجعة الكود)
المزودون (Gemini/Groq/NIM) صاروا يقرأون مفاتيحهم **عند كل نداء** بدل وقت الإنشاء، فلا تبقى نسخة مهيّأة بإعداد قديم — وهو ما أثبتته اختبارات التكامل عند تبديل البيئة.

## 3) الخطوة التالية مباشرةً: البحث الدلالي (RAG)

**الشكل:** أداة قراءة فقط `search_knowledge` تُسجَّل في `McpToolRegistry`، فتورث تلقائيًا البوابات السبع (علم، سماح، سقف، تحقق، مهلة، اقتصاص، تدقيق) بلا مسار تنفيذ جديد.

**المصدر الأول (بلا مفاتيح وبلا كلفة):** الأسئلة الشائعة + بيانات المتجر + مرادفات عربية مضبوطة (مثال: «مطهر/ديتول/كلوركس» → نفس العائلة).

**المعيار الحاسم:** استعلام «عايز حاجة تعقيم» يجب أن يعيد كلوركس/مطهرات ولو لم يذكر العميل الاسم الحرفي.

```
ENABLE_RAG=false        ⇒ لا شيء يتغير (أداة غير مرئية، صفر تنفيذ)
ENABLE_RAG=true         ⇒ search_knowledge متاحة للقراءة فقط، بحدود MCP نفسها
```

**التوسعة لاحقًا بلا تغيير عقد:** نفس الأداة يمكن أن تتحدث إلى خدمة استرجاع خارجية (NeMo Retriever أو أي خدمة متوافقة) عبر `RAG_SERVICE_URL` **https فقط**؛ الأداة عقد ثابت، والمصدر قابل للتبديل.

**القياس (بنمط `rag-eval`):** معدل إصابة النتائج الصحيحة (hit@3) وزمن الاستجابة p50/p95، مع سقف مهلة الأداة المركزي 4 ثوانٍ كما هو.

## 4) إرسال الصور — التصميم قبل التنفيذ

| البند | القرار المقترح |
|---|---|
| العلم | `ENABLE_IMAGE_UPLOAD` (افتراضيًا مغلق) |
| الحجم والأنواع | صور jpg/png/webp فقط، حد صريح للحجم، والتحقق من النوع الحقيقي في السيرفر لا بالامتداد |
| الخصوصية | لا تخزين دائم افتراضيًا؛ إزالة بيانات EXIF؛ لا معالجة لأي محتوى شخصي |
| الحدود | حد معدل مستقل + حد أقصى لعدد الصور لكل رسالة |
| الاستخدام | «اعرف المنتج من الصورة» → يُرجع اقتراحًا من الكتالوج، أو يحوّل للواتساب عند الفشل |
| التراجع | حذف العلم ⇒ يختفي زر الصورة ويعود كل شيء كما كان |

> ملاحظة فنية مهمة: مهارات `deepstream-*` من NVIDIA موجّهة إلى **تحليل الفيديو/الرؤية بخطوط DeepStream** (كاميرات ومراقبة)، لا إلى رفع صور في متجر إلكتروني. الأنسب لرفع الصور هو نقطة نهاية نموذج رؤية-لغة (VLM) عبر NIM نفسه، لذا هذا البند مؤجّل حتى نضبط قرار التخزين والخصوصية.

## 5) متابعة الطلبات — بتشديد أمني مقصود

الحالة الحالية: `GET /api/orders` محمي بجلسة الإدارة فقط (لا يُتاح للعملاء) — وهذا مقصود. أي فتح للعميل يجب أن يمنع **تعداد الطلبات** (تخمين أرقام الطلبات وقراءة بيانات غيره):

- أداة واحدة `track_order` تعمل فقط بعاملين معًا: **رقم الطلب + آخر 4 أرقام من الهاتف**.
- الإخراج: حالة الطلب + ملخص مبهم (بلا عنوان ولا هاتف كامل ولا قائمة أسعار مفصلة).
- حد معدل صارم مستقل (مثال: 5 محاولات/10 دقائق) + تسجيل المحاولات الفاشلة.
- رسالة الفشل **واحدة** لا تكشف إن كان الرقم موجودًا أم لا.
- العلم: `ENABLE_ORDER_TRACKING` (مغلق افتراضيًا).

## 6) التحليلات وسلوك البحث

- المصدر: `chat_logs` الموجود أصلًا + عدّاد داخلي للاستعلامات المتكررة.
- القاعدة: **تجميع مجهول الهوية فقط** (الأكثر تكرارًا من الكلمات/الأنماط)، بلا ربط بأي هوية، ومدة احتفاظ محددة.
- المخرج: أقتراحات Quick Chips تُبنى من الأكثر بحثًا، تُراجع يدويًا قبل الظهور (لا تُولّد نصوصًا تُعرض للعميل آليًا).

## 7) مهارات NVIDIA: ما ينطبق على مشروعنا فعلًا

المهارات مثبَّتة في مستودع رسمي: `npx skills add nvidia/skills` (و`--list` للاستعراض، و`--skill <name> --yes` لتثبيت واحدة).
مهم أن نكون دقيقين: **هذه مهارات لوكلاء البرمجة (تعليمات وأدوات تطوير)، ليست حزمًا تعمل داخل تطبيق Next.js على Vercel.**

| المهارة | ما هي فعلًا | كيف نستفيد منها في مشروعنا |
|---|---|---|
| `nemo-retriever` | CLI/خدمة بايثون للفهرسة والاسترجاع من المستندات (LanceDB/خدمة) | **لاحقًا وباختيارنا:** تشغيل خدمة استرجاع خارجية واستدعاؤها من أداة `search_knowledge` عبر رابط https — العقد لا يتغير |
| `rag-blueprint` | دليل نشر/ضبط/تشخيص بلوبرنت RAG (Docker/Helm) | مرجع تطويري لشكل طبقة الاسترجاع ومكوّناتها عندما ننتقل لاسترجاع متجهي |
| `rag-eval` | تقييم جودة RAG (مقاييس RAGAS) | نبني منه مجموعة تقييم صغيرة (أسئلة متجر + الإجابة المتوقعة) ونقيس hit@3 قبل/بعد |
| `rag-perf` | ضبط الأداء وزمن الاستجابة | مسطرة قياس p50/p95 للاستدعاء المحكوم، مع بقاء المهلة المركزية 4 ثوانٍ |
| `data-designer` | توليد بيانات تدريب/تقييم اصطناعية | توليد مجموعة أسئلة مصرية متنوعة لتقييم سيليا والاقتراحات السريعة |
| `deepstream-dev` / `deepstream-import-vision-model` | خطوط تحليل فيديو ورؤية (DeepStream) | لا تنطبق على متجر إلكتروني؛ تبقى خيارًا فقط لو صار عندنا تحليل كاميرات/فيديو، وليست بديلًا عن رفع صور العملاء |

**التنصيب (أداة تطوير، لا تدخل حزمة التطبيق):**

```bash
npx skills add nvidia/skills --list                       # استعراض الكتالوج
npx skills add nvidia/skills --skill rag-eval --yes       # مثال: تقييم RAG
npx skills add nvidia/skills --skill nemo-retriever --yes # مثال: خدمة استرجاع لاحقًا
```

> لا شيء من هذه المهارات يُضاف إلى `package.json` أو إلى مسار النشر؛ الكود الذي نكتبه يبقى نمطيًا بلا اعتماديات جديدة على وقت التشغيل.

## 8) البروتوكول الثابت لكل بند من هذه المراحل

1. **علم ميزة مستقل** افتراضيًا مغلق.
2. **صفر تغيير في العقد** إلا بحقل إضافي اختياري (كما فعلنا مع `products`).
3. **اختبارات قبل الدمج**: انفتاح الميزة + إغلاقها + الفشل الصامت + عدم تسريب أي سر.
4. **حدود مركزية** (سقف/مهلة/حجم) لا تستطيع أي أداة توسيعها.
5. **التراجع إعداد لا كود**.
