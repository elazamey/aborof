# CeliaTokenManager — توكنات وكيل مُدارة بالنطاقات (تصميم + تنفيذ)

> **الحالة:** تصميم معتمد ومكتوب قبل الكود، ثم نُفِّذ في نفس الفرع (هجرة `0004`، الوحدة، مساران إداريان، واجهة، 22 اختبارًا، وبوابتان جديدتان).
> **التاريخ:** 2026-09-29 · **الفرع:** `arena/01a0ed13-aborof`
> **يخلف:** التوكن الوحيد في البيئة `CELIA_AGENT_TOKEN` (يبقى مدعومًا للتعايش).

## 2) القرار المعماري

| القرار | البديل المرفوض | لماذا |
|---|---|---|
| توكنات مُدارة في **Turso** (جدول `celia_tokens`) | إبقاء التوكنات في متغيرات البيئة | البيئة لا تحمل هوية/نطاق/تاريخًا لكل توكن، ولا تُلغي جزئيًا |
| **البصمة فقط** تُخزَّن (SHA-256) | تخزين النص الصريح أو بصمة بطيئة | التوكن عشوائي 256 بت — لا يُكسر بالقوة الغاشمة، فالبطء بلا مقابل (انظر §5) |
| **علم منفصل** `ENABLE_CELIA_TOKENS` (مغلق افتراضيًا) | تمكين ضمني | نفس نمط `ENABLE_RBAC` و`ENABLE_CELIA_AGENT` — الغياب = تعطيل |
| **تعايش** مع `CELIA_AGENT_TOKEN` عند التمكين | حذف التوكن القديم | لا يكسر مستهلكًا قائمًا؛ الاثنان يمران عبر نفس البوابات |
| **إلغاء بلا حذف فيزيائي** | `DELETE` من الجدول | الإلغاء واقعة تدقيق يجب أن تبقى (`revoked_at`, `revoked_by`) |
| **كشف واحد** للنص الصريح عند الإنشاء/التدوير | إمكانية إعادة العرض لاحقًا | لا يوجد ما يُعاد عرضه: النص الصريح غير مخزَّن أصلًا |

## 3) نموذج البيانات — هجرة `0004_celia_tokens`

```sql
CREATE TABLE IF NOT EXISTS celia_tokens (
  id            TEXT PRIMARY KEY,              -- معرّف عام: ct_<12 hex>
  label         TEXT NOT NULL,                 -- اسم وصفي عربي/لاتيني
  token_prefix  TEXT NOT NULL,                 -- cel_XXXXXXXX — للعرض فقط
  token_hash    TEXT NOT NULL UNIQUE,          -- SHA-256 hex (64)
  scopes        TEXT NOT NULL DEFAULT '[]',    -- مصفوفة JSON من كتالوج النطاقات
  status        TEXT NOT NULL DEFAULT 'active',-- active | revoked
  created_by    TEXT NOT NULL,                 -- هوية الفاعل من RBAC
  use_count     INTEGER NOT NULL DEFAULT 0,
  expires_at    INTEGER NOT NULL DEFAULT 0,    -- 0 = بلا انتهاء (unix ms)
  last_used_at  TEXT,
  revoked_at    TEXT,
  revoked_by    TEXT,
  created_at    TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK (length(trim(label)) >= 2 AND length(label) <= 60),
  CHECK (id GLOB 'ct_[0-9a-f]*' AND length(id) BETWEEN 6 AND 40),
  CHECK (token_prefix GLOB 'cel_*' AND length(token_prefix) BETWEEN 12 AND 20),
  CHECK (length(token_hash) = 64 AND token_hash GLOB '[0-9a-f]*'),
  CHECK (json_valid(scopes) AND json_type(scopes) = 'array' AND length(scopes) <= 2000),
  CHECK (status IN ('active','revoked')),
  CHECK (expires_at >= 0),
  CHECK (use_count >= 0)
);
CREATE INDEX IF NOT EXISTS idx_celia_tokens_status ON celia_tokens(status);
```

**قرارات القيود:** القيود هنا ليست تجميلًا — هي ما يجعل صفًّا فاسدًا مستحيلًا حتى لو جاء من خارج طبقة التطبيق (سكربت صيانة، استعلام يدوي، هجرة معطوبة). البصمة بنص hex صغير وبطول مثبَّت 64 (`GLOB` + `length`) تمنع تخزين أي شيء آخر في هذا العمود بالخطأ، و`UNIQUE` عليها يحوّل تكرار التوكن إلى استحالة رياضية لا إلى مراجعة بشرية.

## 4) دورة الحياة

```
إنشاء (celia:manage)                استخدام                        إنهاء
──────────────────►  النص الصريح يُعرض مرة واحدة  ──►  تدقيق + use_count
        │            (ثم لا يُخزَّن ولا يُسجَّل)         last_used_at
        │
        ├── تدوير: توكن جديد + إلغاء القديم في معاملة واحدة ──► كشف واحد للجديد
        ├── إلغاء يدوي (409 إن كان ملغى أصلًا)
        └── انتهاء زمني: expires_at>0 ويُقيَّم عند كل طلب ⇒ 401
```

**عند كل طلب:** البحث بالبصمة ← التحقق من الحالة والانتهاء ← **تقاطع** نطاقات التوكن مع سقف المتجر ← تمرير النطاقات الفعلية إلى `ScopeGuard`.

## 5) رياضيات الأمان والصيغة

| البند | القرار | التبرير |
|---|---|---|
| العشوائية | `randomBytes(32)` = **256 بت** من CSPRNG | فضاء بحث `2^256` — الاستنفاد غير ممكن |
| الصيغة | `cel_` + `base64url(32B)` = 47 حرفًا | بادئة مميزة تُسهِّل الكشف الآلي عن تسريبها (secret scanning) |
| التخزين | `SHA-256(token)` hex | التوكن **عالي العشوائية** لا يحتاج دالة بطيئة: scrypt هنا يضيف ~50ms/طلب وCPU بلا أي مكسب أمني (خلاف كلمة المرور البشرية في `password.ts`) |
| المقارنة | مساواة بصمة عبر فهرس `UNIQUE` | لا يوجد تسريب زمني ذو معنى: ما يُقارَن قيمة مشتقة من سر 256 بت، واختلاف الزمن لا يقرّب المهاجم من النص |
| العرض | `token_prefix` = أول 12 حرفًا | يكفي للتمييز البصري في اللوحة، **لا يكفي** لإعادة التركيب (باقي 35 حرفًا مجهول) |
| النص الصريح | يُعاد مرة واحدة في استجابة الإنشاء/التدوير، ولا يُخزَّن ولا يُسجَّل ولا يُعاد | لا توجد نسخة يمكن تسريبها لاحقًا |

## 6) مصفوفة النطاقات — ثلاثة سقوف

**السقف 1 — الكتالوج.** النطاقات المسموحة هي `CELIA_KNOWN_SCOPES` **بعد إصلاح الثغرة رقم 6**: إضافة `chat:write` المفقود. أي نطاق خارج الكتالوج يُرفض عند الكتابة.

**السقف 2 — مانح التوكن (anti-escalation).** لا يمنح الفاعل نطاقًا يزيد عن صلاحياته: كل نطاق يُسقَط إلى صلاحية RBAC واحدة أو أكثر يجب أن يملكها المانح (أو يملك `*`):

| النطاق | صلاحية RBAC اللازمة لمنحه |
|---|---|
| `products:read` · `products:write` | `products:write` |
| `orders:read` · `orders:write` | `orders:read` · `orders:write` (كلٌّ بنفسه) |
| `admin:read` | `admin:read` |
| `mcp:read` · `mcp:write` | `mcp:read` |
| `faq:read` · `faq:write` · `chat:read` · `chat:write` | `celia:manage` (ملك سيليا نفسها) |

**السقف 3 — المتجر (وقت الطلب).** حتى لو مُنح توكن نطاقًا ما، فالنطاق الفعلي = **تقاطع** نطاقاته مع `CELIA_ALLOWED_SCOPES`. رفع السقف قرار بيئة لا يملكه حائز التوكن — فشل مغلق في الاتجاهين.

## 7) الاندماج مع المصادقة والـScopeGuard

| الملف | التغيير |
|---|---|
| `src/lib/celia/auth.ts` | مسار ثالث عند `ENABLE_CELIA_TOKENS=true`: Bearer ← بصمة ← قاعدة البيانات. الترتيب: جلسة الإدارة ← توكن مُدار ← توكن البيئة (تعايش). يُعاد `scopes` في كائن الهوية |
| `src/lib/celia/scope-guard.ts` | `createCeliaScopeGuard(ceiling?)` — عند تمرير سقف (نطاقات التوكن) يصبح المسموح = **تقاطع** السقف مع سقف المتجر |
| `src/app/api/celia/chat/route.ts` | بعد حسم الهوية: `guard` الفعلي مشتق من نطاقات الفاعل — توكن بلا `chat:write` يُرفض 403، وجلسة الإدارة تبقى على سلوكها اليوم |
| `src/lib/rbac/permissions.ts` | صلاحيتان جديدتان: `celia:read` (عرض التوكنات) و`celia:manage` (إنشاء/إلغاء/تدوير) — الكتالوج 10 ⇒ 12 |
| `src/lib/rbac/store.ts` | تصدير منشئ سطر التدقيق `auditInsertStatement` ليكتبه صاحب التوكنات داخل معاملاته (بلا نسخة موازية من التطبيع/التنقية) |

## 8) نقاط النهاية والعقود

| المسار | الطريقة | الصلاحية | السلوك |
|---|---|---|---|
| `/api/admin/celia/tokens` | `GET` | `celia:read` | القائمة: معرّف، اسم، بادئة، نطاقات، حالة، آخر استخدام، عدّاد — **بلا بصمة ولا نص صريح** |
| `/api/admin/celia/tokens` | `POST` | `celia:manage` | إنشاء ← **الكشف الوحيد** للنص الصريح |
| `/api/admin/celia/tokens` | `PATCH` | `celia:manage` | `{id, action:"revoke"|"rotate"}` — نفس نمط مسارات RBAC (بلا مسارات ديناميكية)، والتدوير يعيد الكشف مرة أخرى للجديد |

كلها: 404 عند إغلاق `ENABLE_CELIA_TOKENS` وحده (يمكن تجهيز التوكنات قبل تفعيل الوكيل نفسه)، و401 بلا جلسة، و403 بلا صلاحية، و422 لعقد مخالف، وحدّ معدل كتابي، وسطر تدقيق بمعرّف الفاعل.

## 9) الواجهة — `CeliaTokenManager`

تبويب «🔑 توكنات سيليا» في `/admin`:
- **مصفوفة النطاقات**: خيارات مجمّعة (كتالوج/طلبات/أسئلة/محادثات/إدارة/أدوات) + قوالب جاهزة (قراءة فقط، دعم، تشغيل كامل) تختار سقفًا لا تتجاوزه الواجهة.
- **الكشف الواحد**: بطاقة بارزة بعد الإنشاء/التدوير بزر نسخ وتحذير صريح «لن يُعرض مرة أخرى»، وتختفي عند إعادة التحميل (لأن القيمة غير موجودة في القائمة أصلًا).
- **جدول التوكنات**: البادئة، الاسم، النطاقات، الحالة، آخر استخدام، وأزرار إلغاء/تدوير مع تأكيد.
- **حالة العلم**: إن كان `ENABLE_CELIA_TOKENS` مغلقًا تظهر رسالة صريحة أن الميزة معطّلة (الواجهة لا تخفي السبب).

## 10) التدقيق

| الحدث | المُعرّف | التفاصيل |
|---|---|---|
| إنشاء | `celia.token_created` | `label`, `scopes`, `expiresAt`, `prefix` — بلا نص صريح ولا بصمة |
| إلغاء | `celia.token_revoked` | `label`, `prefix` |
| تدوير | `celia.token_rotated` | `prefix` الجديد + القديم |
| رفض صلاحية/نطاق | `rbac.denied` (القائم) | المسار والصلاحية — نفس معمارية M1 |

كل السطور تمرّ عبر `sanitizeAuditDetails` القائم: أي مفتاح يطابق `password|hash|secret|token` يُستبدل بـ`[REDACTED]` — لذا لا تُستخدم في التفاصيل مفاتيح بهذه الأسماء (درس M1: `passwordSource`).

## 11) الاختبارات والبوابات المضافة

**اختبارات:** توليد (طول/بادئة/عشوائية/بصمة)، عدم تخزين النص الصريح، كشف واحد، مصادقة صالحة/مجهولة/ملغاة/منتهية، تقييد النطاقات (403)، السقف المتجري، anti-escalation، التدوير الذرّي، وكتابة التدقيق بلا أي سر.

**بوابات:** `@/lib/celia/tokens` وحدة **خادم فقط** (لا تُستورد في مكوّن عميل)، و`token_hash` لا يُلمس خارج `src/lib/celia/tokens.ts` (نفس نمط `password_hash`)، ووعد الكتالوج ↔ الفرض يبقى اتجاهين.

## 11.b) التحقق الحي (خادم إنتاجي فعلي — Next.js 16 build + SQLite/Turso)

نُفِّذ على `next start` مع `ENABLE_RBAC=true` و`ENABLE_CELIA_TOKENS=true` و`ENABLE_CELIA_AGENT=true`
و`CELIA_ALLOWED_SCOPES=chat:write,products:read`، والنتائج الفعلية:

| السيناريو | النتيجة المقيسة |
|---|---|
| `GET /api/admin/celia/tokens` بلا جلسة | `401` |
| إنشاء توكن `chat:write` بجلسة المالك | `200` + نص صريح بطول **47** حرفًا يبدأ بـ`cel_` |
| القائمة بعد الإنشاء | `false` لكلٍّ من: احتواء النص الصريح، احتواء البصمة، وجود مفتاح `token_hash` |
| `POST /api/celia/chat` بتوكن `chat:write` | `200` مع رد عربي (المسار الحقيقي يعمل) |
| `POST /api/celia/chat` بتوكن `orders:read` فقط | `403` — «نطاقات هذا التوكن لا تتقاطع مع سقف المتجر» |
| التدوير | القديم `401` والجديد `200` في نفس اللحظة |
| الإلغاء | التوكن الملغى `401`، وتكرار الإلغاء `409` |
| دور يملك `celia:manage` فقط يحاول منح `orders:write` | `403` «لا تصعيد صلاحيات»، ومنح `chat:write` مسموح |
| القاعدة مباشرة | `length(token_hash)=64` لكل الصفوف، و**صفر** صف بصيغة غير مطابقة |
| سجل التدقيق | `celia.token_created` بهوية `owner` وبلا أي سر (لا نص صريح ولا بصمة) |
| العلم مغلق (`ENABLE_CELIA_TOKENS=false`) | `404` على GET/POST/PATCH، وتوكن مُدار لا يمرّ على المحادثة (fail-closed) |
