# لوحة الصلاحيات (M1) — أدوار ومستخدمون وسجل تدقيق

> البديل المحكوم لكلمة مرور الإدارة المشتركة: **هوية لكل مستخدم، دور لكل هوية،
> وصلاحية لكل عملية** — مع بوابات تُغلق افتراضيًا، وبلا أي تراجع في السلوك القائم.

## الفكرة في سطر

كان الوضع كلمة مرور واحدة = كل الصلاحيات بلا نسبية ولا أثر. صار: **مستخدمون
مُدارون بأدوار قابلة للتعديل، وكل مسار إداري يفرض صلاحية محدّدة، وكل تغيير
يُكتب في سجل تدقيق بهوية فاعله** — والعلم `ENABLE_RBAC` مغلق افتراضيًا فيبقى
السلوك القديم حرفيًا لمن لا يفتحه.

## جدول الصلاحيات (الكتالوج = نقاط الفرض)

لا توجد صلاحية "للمستقبل": كل صلاحية في `src/lib/rbac/permissions.ts` لها نقطة
فرض فعلية في الكود، وبوابة `security-gates` تفشل إذا انحرف أحد الاتجاهين
(صلاحية بلا حارس، أو حارس بصلاحية غير مدرجة).

| الصلاحية | ما تفتحه | نقطة الفرض |
|---|---|---|
| `orders:read` | عرض الطلبات | `GET /api/orders` |
| `orders:write` | تحديث حالة الطلب | `PATCH /api/orders` |
| `products:write` | إضافة/تعديل/حذف منتج | `POST,DELETE /api/products` |
| `admin:read` | مانيفست أسطول الوكلاء | `GET /api/admin/agents` |
| `mcp:read` | أدوات MCP المسجّلة | `GET /api/admin/mcp/tools` |
| `diagnostics:read` | التشخيص التشغيلي | `GET /api/admin/diagnostics` |
| `rbac:read` | عرض الأدوار والمستخدمين | `GET /api/admin/rbac` |
| `rbac:write` | تعديل الأدوار والمستخدمين | `POST/PATCH/DELETE /api/admin/rbac/{roles,users}` |
| `audit:read` | سجل التدقيق | `GET /api/admin/rbac/audit` |
| `celia:use` | سيليا من جلسة الإدارة | `POST /api/celia/chat` |

الرمز `*` (كل الصلاحيات) **محصور في الدور المدمج `owner`**: العقد يرفضه في أي
دور مخصص، و`normalizeCustomPermissions` يرفضه مرة ثانية في المخزن، والأدوار
المدمجة غير قابلة للتعديل أصلًا (409) فلا يمكن حقنه.

## الأدوار المدمجة (مصدرها الكود، غير قابلة للتعديل أو الحذف)

| الدور | الصلاحيات |
|---|---|
| `owner` — المالك | `*` |
| `operations` — عمليات المتجر | `orders:read`, `orders:write`, `products:write`, `admin:read`, `mcp:read`, `celia:use` |
| `support` — خدمة العملاء | `orders:read`, `orders:write`, `celia:use` |
| `viewer` — قراءة فقط | `orders:read`, `admin:read`, `mcp:read` |

سبب تحصين المدمجة: هي شبكة الأمان التي تعرفها المراجعة سلفًا؛ التعديل والتوسّع
يكونان في **أدوار مخصصة** (`POST /api/admin/rbac/roles`) تحمل معرّفًا لاتينيًا
مستقرًا + اسمًا عربيًا للعرض.

## حصانة الإغلاق (anti-lockout) — أربع قواعد

1. **آخر حائز فعّال على `rbac:write` محصّن**: لا يمكن نزع دوره، ولا تعطيله، ولا
   حذفه (`409 CONFLICT`) — ولا حتى بنزع الصلاحية من الدور نفسه إن كان هو مصدرها.
   القاعدة تُطبَّق **داخل نفس المعاملة** التي تُجري التغيير، فالفحص والكتابة
   عملية واحدة لا يفصلها طلب آخر.
2. **الأدوار المدمجة غير قابلة للتعديل أو الحذف** — لا طريقة لإذابة صلاحيات
   المالك أو حذف دور الكسر الزجاجي.
3. **لا يُحذف دور مُسنَد لمستخدمين** — تُمنع المستخدمون اليتامى بنيويًا
   (`ON DELETE RESTRICT` في الهجرة + فحص صريح قبل الحذف).
4. **لا تصعيد ذاتي**: من لا يملك `rbac:write` لا يستطيع تغيير دوره أو حالته —
   الطلب الوحيد المسموح له هو تغيير **كلمة مرور نفسه** مع إثبات كلمة المرور
   الحالية (`currentPassword`)، وأي حقل آخر ⇒ `403`.

## الدخول والجلسات

| | العلم مغلق | العلم `ENABLE_RBAC=true` |
|---|---|---|
| المُدخل | `{ password }` (كلمة المرور المشتركة) | `{ username, password }` من `rbac_users` |
| الجلسة | v1: `<issuedAt>:<nonce>` بلا هوية | v2: `v2:<userId>:<tokenVersion>:<issuedAt>:<nonce>` |
| الصلاحيات | كل الصلاحيات (مشغّل مفرد) | محسوبة من دور المستخدم |
| الجلسات القديمة | مقبولة | **مرفوضة (401)** — لا مسار خلفي بكلمة المرور المشتركة |

- **التهيئة الأولى (bootstrap):** إن كان جدول المستخدمين فارغًا تمامًا، يُقبل
  الدخول باسم `owner` وكلمة مرور الإدارة المشتركة **مرة واحدة** لإنشاء المالك
  (`password_source = 'bootstrap'` فينبّه الـ UI إلى تغييرها). تُغلق البوابة
  نهائيًا بمجرد وجود مستخدم واحد، ولا تُقبل كلمة المرور المشتركة بعدها أبدًا.
- **الرسائل موحّدة:** حساب غير موجود، وكلمة مرور خاطئة، وحساب معطّل ⇒ نفس
  الـ401 ونفس النص؛ ومع غياب الحساب يُنفَّذ `scrypt` على بصمة وهمية (`DUMMY_HASH`)
  حتى لا يفرّق التوقيت بين الحالتين (منع تعداد الحسابات).
- **ثلاث بوابة معدّل:** 8 محاولات/10 دقائق لكل IP، و10 لكل اسم مستخدم (مفتاحه
  بصمة `sha256` مبتورة فلا يُخزَّن الاسم)، **وقفل الحساب** 15 دقيقة بعد 5
  محاولات فاشلة ⇒ `429` مع `retry_after_seconds`.
- **إبطال فوري:** تغيير كلمة المرور أو الدور أو الحالة يرفع `token_version`،
  فيصبح كل توكن قائم لذلك المستخدم غير صالح فورًا (بلا قائمة إبطال منفصلة).
  ومن يغيّر كلمة مروره بنفسه تُمسح جلسته الحالية ويُطلب منه الدخول من جديد.

## جدول قاعدة البيانات (الهجرة `0003_rbac`)

| الجدول | الأعمدة الجوهرية | القيود |
|---|---|---|
| `rbac_roles` | `id`, `label`, `description`, `permissions` (JSON), `builtin` | معرّف لاتيني، `json_valid` و`json_type='array'`، `builtin IN (0,1)` |
| `rbac_users` | `id`, `username` (UNIQUE), `role_id` (FK), `password_hash`, `password_source`, `status`, `token_version`, `failed_attempts`, `locked_until` | اسم فريد، `status IN ('active','disabled')`، طول البصمة 40–400، `ON DELETE RESTRICT` |

- **كلمة المرور:** بصمة `scrypt$N$r$p$salt$hash` (N=16384, r=8, p=1) مع ملح
  عشوائي 16 بايت لكل كلمة مرور، ومقارنة `timingSafeEqual`. لا نص صريح ولا
  دالة تجزئة سريعة في أي مكان (بوابة static تمنع `createHash/md5/sha1` في وحدة
  كلمات المرور).
- **لا بصمة تغادر طبقة المخزن:** كل كائن يُعاد للخارج (`RbacUserPublic`) بلا
  `password_hash`، وبوابة static تمنع ذكر اسم العمود في مسارات API أو مكوّنات
  العميل. واختبار يفحص أن استجابة اللوحة لا تحوي `scrypt` ولا كلمة المرور.

## التدقيق

`admin_audit_log` هو السجل الوحيد، للإضافة فقط، بلا أي نقطة تعديل أو حذف:

- **الأحداث:** `rbac.role_create|role_update|role_delete`،
  `rbac.user_create|user_update|user_delete`، `rbac.login_success|login_failure`،
  `rbac.denied` (كل رفض صلاحية بصلاحيته الناقصة والمسار المطلوب)، وتُضاف إليها
  أحداث المنتجات والطلبات القائمة بمعرّف الفاعل بدل `admin` الثابت.
- **الكتابة في نفس المعاملة** للتغيير ⇒ لا تغيير بلا أثر، ولا أثر لتغيير لم يحدث.
- **تنقية قبل الكتابة:** `sanitizeAuditDetails` يستبدل أي مفتاح يشبه
  (`password|hash|secret|token`) بـ`[REDACTED]` ولو كان متداخلًا — دفاع مستقل عن
  انتباه منادٍ مستقبلي.
- فشل كتابة سطر `rbac.denied` **لا** يحوّل 403 إلى 500: الطلب مرفوض أصلًا،
  ويُكتفى بسجل خادم مُنقّى.

## الفحوص التي لا تُخترق (محميّة باختبارات)

- `ENABLE_RBAC` مغلق ⇒ `404` موحّد على كل مسارات اللوحة، والسلوك القديم حرفيًا
  (جلسة v1 تعمل، ولا اطّلاع على وجود النقاط).
- `ENABLE_RBAC=true` + جلسة v1 ⇒ `401` (لا مسار خلفي بالكلمة المشتركة).
- مستخدم بصلاحية `orders:read` فقط ⇒ `200` على قراءة الطلبات، و`403` على
  الكتابة، وعلى المنتجات، وعلى اللوحة، وعلى سجل التدقيق، وعلى سيليا.
- لا حذف/تعطيل/نزع لآخر حائز لصلاحية الحكم، ولا تعديل/حذف لدور مدمج.
- لا تصعيد ذاتي: تغيير دور النفس أو حالتها ⇒ `403`، وتغيير كلمة المرور بلا
  `currentPassword` الصحيحة ⇒ `401`.
- حقول زائدة أو صلاحية مجهولة أو كلمة مرور أقل من 12 حرفًا ⇒ `422`.
- محاولات فاشلة متكررة ⇒ قفل مؤقت `429`، ورسالة موحّدة بين الحساب المجهول
  والحساب الخاطئ.
- لا ظهور لأي بصمة أو سر في أي استجابة، ولا في حزمة العميل.

## التشغيل والتراجع

```bash
# تشغيل (Vercel → Production ثم إعادة نشر)
vercel env add ENABLE_RBAC production   # true
# أول دخول: /admin باسم owner وكلمة مرور الإدارة المشتركة ⇒ إنشاء المالك
# ثم: غيّر كلمة المرور، وأنشئ الأدوار/المستخدمين من تبويب «الصلاحيات».

# التراجع الفوري (بلا نشر كود): احذف العلم أو اضبطه على أي قيمة غير true
vercel env rm ENABLE_RBAC production
```

**ماذا يحدث عند التراجع؟** تعود جلسة v1 بكلمة المرور المشتركة للعمل حرفيًا كما
قبل، وتبقى الجداول والسجل كما هي بلا حذف. الجلسات v2 القائمة تصبح غير مستخدمة
(النظام لا يقرأ الهوية في وضع الإغلاق)، فيحتاج المشغّل إلى الدخول بكلمة المرور
المشتركة. لا هجرة عكسية ولا بيانات تُفقد.

**ملاحظة تشغيلية مقصودة:** `ADMIN_PASSWORD` تبقى إلزامية في الوضعين (تشخيص
التهيئة وبوابة التهيئة الأولى)، لكنها تصبح بلا أثر بعد bootstrap — كلمات المرور
بعد ذلك تُدار من اللوحة، وتغيير المتغير في البيئة لا يغيّر كلمة مرور أي مستخدم.
