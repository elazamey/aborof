# Storefront Excellence Engineer

هذه الوثيقة هي معيار تشغيل لتحسين متجر أبو رفيدة العزامي. الغرض منها تحويل مراجعة الواجهة والكود إلى دورة قابلة للقياس، لا إلى إعادة تصميم حسب الذوق.

## القاعدة الحاكمة

لا يُقبل أي تغيير في الواجهة أو عقد API إلا إذا كان لديه دليل، ووصف مشكلة، وأثر متوقع، وتنفيذ محدد، وفحص قبل/بعد، واختبار تراجعي.

> Route غير مكتشف = Route غير موثوق.

## دورة العمل الإلزامية

| المرحلة | المطلوب | المخرج |
|---|---|---|
| DISCOVER | استخراج صفحات Next.js، API routes، الروابط، النماذج، الاستدعاءات، ومسارات الإدارة | `npm run routes:inventory` ومصفوفة مسارات |
| AUDIT | فحص الوظائف، UX، UI، Responsive، RTL، Accessibility، الأداء، SEO، الأمان، والتحويل | Issues مصنفة P0/P1/P2 |
| PRIORITIZE | P0 يمنع الاستخدام أو يسبب خسارة أو ثغرة؛ P1 يؤثر بوضوح؛ P2 تحسين مستقبلي | Backlog مرتب |
| IMPLEMENT | تعديل حقيقي محدود النطاق مع الحفاظ على عقود API | Pull Request مرتبط بمشكلة |
| VERIFY | اختبار Browser وMobile وDesktop وConsole وNetwork وAPI وScreenshots | دليل تحقق قابل لإعادة التشغيل |
| REGRESSION | فحص الوظائف السابقة وGate A/Gate B | قرار PASS/FAIL |
| MEASURE | مقارنة قبل/بعد في الأخطاء، الأداء، UX، والتحويل | أرقام أو ملاحظات قابلة للمقارنة |
| RELEASE | نشر فقط عند اكتمال البوابات | GO أو NO-GO |

## مصفوفة التدقيق

يجب أن يغطي كل تدقيق: بنية React/Next، نظام التصميم، تجربة الكتالوج والمنتج والسلة، RTL العربية، الشاشات بعروض 390 و768 و1440 بكسل، الوصول بلوحة المفاتيح والتباين، صور وخطوط وأداء JavaScript، SEO، حماية الإدارة والطلبات، وسلامة الأسعار والمخزون.

## اكتشاف المسارات

تشغّل الأداة التالية من جذر المشروع:

```bash
npm run routes:inventory
```

وهي تستخرج ملفات `page` و`route` من `src/app` وتعرض نوع المسار وحاجته إلى المصادقة وإشارة استخدام قاعدة البيانات. يجب تحديث المصفوفة عند إضافة route جديد، مع إضافة اختبار أو دليل تحقق له.

## مراجعة بصرية

المسار القياسي هو: فتح الصفحة الرئيسية، الأقسام، المنتج، إضافة إلى السلة، السلة، الطلب، لوحة الإدارة، ثم إعادة الخطوات على الهاتف وسطح المكتب. يجب تسجيل أي overflow أو مشكلة RTL أو CLS أو اختلاف في ارتفاع البطاقات أو غياب focus واضح كـ Issue مع Screenshot وviewport.

## بوابات الجودة

لا يُقبل الدمج ما لم تنجح ESLint وTypeScript والبناء وفحص المسارات والاختبارات الوظيفية المتاحة. لا يكفي نجاح البناء لإثبات صحة الطلبات؛ يجب اختبار رفض جلسة الإدارة، رفض البيانات غير الصالحة، وإعادة حساب السعر والمخزون من الخادم.

## نموذج قرار التغيير

قبل التنفيذ، يجب الإجابة عن الأسئلة التالية: ما المشكلة المثبتة؟ ما المسار أو المكوّن المتأثر؟ ما الأثر المتوقع؟ ما الذي لن يتغير؟ كيف ستُقاس النتيجة؟ وما اختبار التراجع إذا فشل التغيير؟

## المهارات المتخصصة المقترحة

يُستخدم هذا المنسق مع مراجعات متخصصة لـ Frontend Architecture، UI/UX، Visual Design System، E-commerce UX، Responsive/RTL، Visual QA، Accessibility، Performance، SEO، Product Page، والـ Conversion. لا تُنفّذ إعادة تصميم شاملة دفعة واحدة؛ كل تغيير يجب أن يكون صغيرًا، قابلًا للمراجعة، وقابلًا للعكس.
