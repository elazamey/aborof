## 2) كيف قيست هذه الصفوف (بلا أسرار في أي مخرج)

بيئة الوكيل لا تملك `TURSO_AUTH_TOKEN` ولا اتصالًا شبكيًا بـ Vercel، فأُنشئ مسار قياس يملك السرّ بدلًا منها:

| المكوّن | الوظيفة |
|---|---|
| `.github/workflows/turso-evidence.yml` | مجسّ **قراءة فقط** على `pull_request` و`workflow_dispatch`. وظيفة أولى تقرأ أسرار نطاق المستودع، وثانية تعمل **فقط** عند غيابها لتجرّب بيئة `production` وتقول أيّ النطاقين مضبوط (النتيجة: **الأسرار مضبوطة على بيئة `production` فقط**). |
| `scripts/probe-turso-ci.sh` | يشغّل `scripts/verify-turso.mjs`، يطبع الجدول في السجل والملخّص، **وينشره تعليقًا على طلب الدمج** (يُحدَّث في كل تشغيل) — لأن سجلات Actions تُقدَّم بروابط على مضيف تخزين لا تصل إليه كل بيئات القراءة. |
| `scripts/lib/db-url.mjs` | تشخيص آمن: مخطّط الرابط، نوع المضيف (Turso؟ لوحة تحكم؟ قيمة موضعية؟)، طول المضيف، **شكل مقاطع المسار بالأطوال فقط** (مثال `8/9/5`)، واشتقاق روابط اتصال مرشّحة من رابط اللوحة — بلا طباعة أي قيمة. |
| `scripts/verify-turso.mjs` | صار يطبع الجدول في **كل** الحالات (حتى فشل الاتصال)، ويصنّف فشل كل رابط مشتق (`DNS` / `رمز مرفوض` / `لا قاعدة بهذا الاسم`) برسالة مُنقّاة. |

**ضمانات عدم الكشف:** الرابط والرمز داخل قائمة حجب (`redact`) قبل أي طباعة؛ ما ظهر في التعليق هو *أطوال* المقاطع ونوع النطاق وحالة HTTP فقط. الفحص كله `SELECT`/`GET` — لا هجرة ولا كتابة ولا لمس لـ `ensureSchema`.

**الأداة أدلة لا بوابة:** حالة قاعدة الإنتاج لا تُحمرّ نقطة التحقق في طلب الدمج (وإلا بدا كل طلب مكسورًا لإعداد خارجي)، لكن الفشل يُعلَن مرتين: التعليق بالجدول كاملًا، وإشعار `::error::` في تبويب الفحوص. البوابة الحاجبة تبقى «Quality and Security».

**تحقق محلي (نفس المسار بلا أسرار):** على قاعدة ملف جديدة — `7` صفوف بالسلوك المتوقع وكود خروج `1` عند وجود صف أحمر؛ والاختبارات: **234/234 ✅**، `lint` ✅، `typecheck` ✅، `security:gates` ✅ (74 ملفًا)، `sync-migrations --check` ✅.

## 3) السبب الجذري بالتفصيل

1. القيمة المحفوظة ليست `libsql://…` بل `https://app.turso.tech/<org>/databases/<db>` (المضيف `app.turso.tech` طوله 14، ومقاطع المسار `8/9/5` — أي `/org/databases/db`، وطول الرابط 47).
2. توثيق Turso يفرّق صراحةً بين **لوحة التحكم** (`https://app.turso.tech`) وبين **رابط قاعدة البيانات** الذي يُنسخ من زر Connect: `libsql://[DB-NAME]-[ORG-NAME].turso.io` (أو `https://` بنفس المضيف، أو `turso://`).
3. لذلك يقرأ العميل HTML (صفحة تحويل 307 من اللوحة) لا JSON، فيظهر `Unexpected token '<'`.
4. الاشتقاق التلقائي من مقاطع اللوحة جُرّب فعلًا: `store-elazamey.turso.io` ← **400**، و`elazamey-store.turso.io` ← **404** («المضيف موجود ولا قاعدة بهذا الاسم») ⇒ اسم القاعدة الحالي مختلف، أو القاعدة حُذفت/لم تُنشأ على هذه المؤسسة.
5. في Vercel، المتغيرات **لا تنتقل من أسرار Actions**؛ الأرجح أن نفس القيمة الخاطئة مضبوطة هناك أيضًا — وهذا يفسّر بالتحديد ما رصده التشغيل الحيّ: عرض من البذرة، وفشل أي كتابة طلب.

## 4) الإصلاح — خطوتان ثم إعادة تشغيل واحدة

**أ) في Turso:** افتح <https://app.turso.tech> → المؤسسة → Databases.
- إن كانت القاعدة موجودة: افتحها → **Connect** → انسخ **Database URL** (يبدأ بـ `libsql://`) و**Auth Token** (Full access، بلا انتهاء).
- إن لم تكن موجودة (الخطة المجانية تحذف قواعد الخاملة): أنشئ قاعدة بمنطقة `fra` أو `ams`، ثم انسخ الرابط والتوكن منها.

**ب) في مكانين فقط (كلاهما ضروري):**

| المكان | المسار | ما يُضبط |
|---|---|---|
| Vercel (وقت التشغيل) | Project → Settings → Environment Variables → **Production** | `TURSO_DATABASE_URL` (الصيغة `libsql://…`) و`TURSO_AUTH_TOKEN`، ثم **Redeploy** (المتغيرات تُقرأ في بناء/تشغيل جديد) |
| GitHub Actions (المجسّ) | Settings → Environments → **production** → Secrets (أو نطاق المستودع) | نفس القيمتين — بهما يكتمل الجدول تلقائيًا |

**ج) إعادة الفحص (أي واحدة):**
```bash
# يدويًا من تبويب Actions
gh workflow run turso-evidence.yml --ref main
# أو محليًا بأسرار حقيقية (لا تُكتب في ملف متتبَّع):
TURSO_DATABASE_URL='libsql://…' TURSO_AUTH_TOKEN='…' npm run verify:turso
```
النتيجة المتوقعة بعد الإصلاح: `conn ✅ · mig-table ✅ (هجرتان) · mig-parity ✅ · row-7 ✅ · row-8 ✅ · row-9 ✅` (قد يحتاج الصف 9 طلبًا واحدًا قبل أن تُزامَن البذرة)، ثم يصير صف `db-binding` في `smoke:prod` ✅ — أي أن الطلبات الحقيقية تنجح.
